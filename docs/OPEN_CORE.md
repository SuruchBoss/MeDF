# โมเดล Open Core ของ MeDF

MeDF แยกโค้ดเป็นสองชั้นอย่างชัดเจน

| | **ฟรี (Free tier)** | **ฟีเจอร์เสริมแบบชำระเงิน** |
| --- | --- | --- |
| โค้ดอยู่ที่ไหน | repository สาธารณะนี้ | repository ส่วนตัวแยก **ไม่เคยถูก push เข้าที่นี่** |
| ใครอ่านโค้ดได้ | ทุกคน | เฉพาะทีมผู้พัฒนา |
| ผู้ใช้ที่จ่ายเงินได้อะไร | — | **ใช้ฟีเจอร์ได้** (ไม่ได้รับโค้ด) |
| ถ้าไม่มีโมดูลเสริม | ทำงานครบตามปกติ | ฟีเจอร์นั้นไม่ปรากฏและเรียกไม่ได้ |

เป้าหมาย: คนทั่วไป clone repo นี้แล้วได้โปรแกรมแก้ไข PDF ที่ใช้งานได้จริงทั้งชุด
ส่วนฟีเจอร์ที่เป็นรายได้ ไม่มีอยู่ในประวัติ git ของ repo สาธารณะเลย แม้จะ push ใหม่กี่ครั้งก็ตาม

## สิ่งที่ซ่อนได้จริง และสิ่งที่ซ่อนไม่ได้

ข้อนี้สำคัญและต้องเข้าใจให้ตรงกันก่อนออกแบบฟีเจอร์ที่เก็บเงิน

| ประเภทโค้ด | ซ่อนจาก repo สาธารณะ | ซ่อนจากผู้ใช้ที่จ่ายเงิน |
| --- | --- | --- |
| **โค้ดฝั่งเซิร์ฟเวอร์** (`server.transformExport`, `server.handlers`) | ได้ | **ได้** — โค้ดไม่ถูกส่งไปเบราว์เซอร์เลย ผู้ใช้เห็นแค่ผลลัพธ์ |
| **โค้ดฝั่งเบราว์เซอร์** (UI ของฟีเจอร์เสริม) | ได้ | **ไม่ได้** — อะไรที่ส่งไปให้เบราว์เซอร์รัน ผู้ใช้เปิด devtools อ่านได้เสมอ |

นี่เป็นข้อจำกัดของเว็บ ไม่ใช่ข้อจำกัดของ MeDF การ minify หรือ obfuscate ทำให้อ่านยากขึ้นแต่ไม่ได้ทำให้อ่านไม่ได้

**ข้อแนะนำ:** ให้ตรรกะที่เป็นมูลค่าจริงของฟีเจอร์ที่เก็บเงินอยู่ฝั่งเซิร์ฟเวอร์
แล้วให้ฝั่งเบราว์เซอร์เป็นเพียงหน้าตาที่เรียก API เช่น

- ✅ OCR, redaction, การประมวลผลหลายไฟล์, การคิดเลขที่เป็นความรู้เฉพาะ → เซิร์ฟเวอร์
- ⚠️ ปุ่มและฟอร์มสำหรับสั่งงานเหล่านั้น → เบราว์เซอร์ (อ่านได้ แต่ไร้ประโยชน์ถ้าไม่มีสิทธิ์เรียก API)

## โครงสร้าง

```
MeDF (public)
├── apps/web/src/lib/features.ts     ประกาศ "ชื่อ" ฟีเจอร์ทั้งหมด + แพ็กเกจที่ต้องมี
│                                    (ชื่อฟีเจอร์เป็นข้อมูลสาธารณะ — ลูกค้าต้องรู้ว่าจ่ายเพื่ออะไร)
├── apps/web/src/lib/pro.ts          ตัวโหลดโมดูล + สัญญา (interface) + ประตูตรวจสิทธิ์
├── apps/web/src/app/api/pro/[handler]/   ทางเข้าเดียวของฟีเจอร์เสริม (ตรวจสิทธิ์ก่อนเสมอ)
├── apps/web/src/app/api/features/        บอกเบราว์เซอร์ว่าใช้อะไรได้บ้าง
└── scripts/guard-private.mjs        กันโค้ดฟีเจอร์เสริมหลุดเข้า git

medf-pro (private, แยก repository)
├── index.js                         implement สัญญา ProModule
└── ...                              โค้ดจริงของฟีเจอร์ที่เก็บเงิน
```

โค้ดใน repo สาธารณะรู้เพียง **ชื่อฟีเจอร์** และ **รูปร่างของ interface** ไม่รู้ว่าฟีเจอร์ทำงานอย่างไร

## สัญญาของโมดูล (ProModule)

```js
module.exports = {
  id: 'medf-pro',
  version: '1.2.0',

  // ต้องเป็น key ที่ประกาศไว้ใน features.ts ด้วย source: 'private'
  features: ['pro.ocr', 'pro.redact'],

  server: {
    // เรียกหลังจาก core สร้าง PDF เสร็จ — ไม่เคยถูกส่งไปเบราว์เซอร์
    async transformExport(bytes, context) {
      // context = { user: { id, plan }, overlay, documentTitle }
      return await addSearchableTextLayer(bytes);
    },

    // เปิดเป็น POST/GET /api/pro/<ชื่อ> โดยตรวจสิทธิ์ให้แล้ว
    handlers: {
      ocr: {
        feature: 'pro.ocr',
        async handle(request, user) {
          return Response.json({ ok: true });
        },
      },
    },
  },
};
```

กฎที่ตัวโหลดบังคับ:

- โมดูลต้องมี `id`, `version` และ `features`
- ทุก key ใน `features` ต้องมีอยู่ใน `features.ts` มิฉะนั้นโมดูลถูกปฏิเสธทั้งก้อน
  (กันการแอบเปิดฟีเจอร์ที่ไม่ได้ประกาศ)
- ถ้า `transformExport` throw ระบบจะใช้ไฟล์เดิมของ core ต่อ — โมดูลที่พังต้องไม่ทำให้ผู้ใช้ export ไม่ได้

## การตรวจสิทธิ์

ทุกการเรียกฟีเจอร์เสริมผ่านประตูเดียวคือ `canUseFeature(user, key)` ซึ่งเป็นจริงเมื่อ

1. แพ็กเกจของสมาชิกถึงระดับที่ `features.ts` กำหนด **และ**
2. เซิร์ฟเวอร์นี้ติดตั้งโมดูลที่ implement ฟีเจอร์นั้นไว้จริง

ผลลัพธ์ที่เป็นไปได้ของ `/api/pro/<name>`

| สถานะ | ความหมาย |
| --- | --- |
| `401` | ยังไม่เข้าสู่ระบบ |
| `402` `feature_locked` | เข้าสู่ระบบแล้วแต่แพ็กเกจยังไม่ถึง |
| `404` | ไม่มี handler ชื่อนี้ในโมดูล |
| `501` `pro_not_installed` | เซิร์ฟเวอร์นี้เป็นบิลด์โอเพนซอร์สล้วน |

การตรวจทั้งหมดอยู่ฝั่งเซิร์ฟเวอร์ การแก้ JavaScript ในเบราว์เซอร์จึงไม่ช่วยให้ข้ามได้

## วิธี deploy โมดูลเสริม

เลือกวิธีใดวิธีหนึ่ง (ตัวโหลดลองตามลำดับนี้)

**1. ชี้ path ตอน deploy — แนะนำ**

```bash
MEDF_PRO_MODULE=/opt/medf-pro/index.js node apps/web/.next/standalone/apps/web/server.js
```

โมดูลถูก mount เข้ามาตอนรัน ไม่เคยอยู่ใน image หรือใน git ของ repo สาธารณะ

**2. แพ็กเกจจาก registry ส่วนตัว**

```bash
npm install @medf/pro --registry https://npm.your-company.com
```

**3. สำเนาสำหรับพัฒนาในเครื่อง**

```bash
npm run pro:scaffold      # สร้าง apps/web/src/pro-private/ (อยู่ใน .gitignore)
npm run dev
```

## การรับประกันว่าโค้ดไม่หลุดเข้า git

สามชั้นซ้อนกัน

1. **`.gitignore`** — ครอบ `**/pro-private/`, `**/medf-pro/`, `**/private-module*/`, `*.pro.ts` และอื่น ๆ
2. **pre-commit hook** — ติดตั้งด้วย `npm run setup:hooks` แล้วทุก commit จะรัน `guard-private.mjs`
   ซึ่งจะ **fail** ถ้าพบไฟล์ pattern เหล่านั้นใน staging หรือใน tracked files
3. **CI** — `npm run guard:private` เป็นขั้นตอนแรกของ workflow `CI`
   ดังนั้นแม้จะ force-push ข้าม hook ในเครื่อง ตัว CI ก็จะจับได้

```bash
npm run setup:hooks     # ทำครั้งเดียวหลัง clone
npm run guard:private   # ตรวจด้วยมือเมื่อไรก็ได้
```

> **ข้อควรระวัง:** ถ้าเคย commit ไฟล์ที่เป็นความลับไปแล้ว การลบใน commit ใหม่ไม่พอ
> เพราะยังอยู่ในประวัติ git ต้องใช้ `git filter-repo` เขียนประวัติใหม่ แล้ว force-push
> และถือว่าโค้ดนั้นรั่วไปแล้ว (ควรถือว่าต้องเปลี่ยน/เขียนใหม่)

## เพิ่มฟีเจอร์แบบชำระเงินใหม่

1. ใน repo สาธารณะ: เพิ่ม entry ใน `apps/web/src/lib/features.ts` โดยตั้ง `source: 'private'`
   และเลือกแพ็กเกจที่ต้องมี — ขั้นนี้เปิดเผยแค่ *ชื่อและคำอธิบาย* ของฟีเจอร์
2. ใน repo ส่วนตัว: implement handler หรือ `transformExport` แล้วเพิ่ม key นั้นใน `features` ของโมดูล
3. ฝั่ง UI (ถ้าต้องมี): เรียก `/api/features` เพื่อรู้ว่าปุ่มควรแสดงหรือไม่ แล้วยิงไปที่ `/api/pro/<name>`
4. อัปเดตหน้าแพ็กเกจให้ลูกค้าเห็นว่าจ่ายแล้วได้อะไร

ฟีเจอร์ที่ประกาศไว้แต่ยังไม่มีโมดูล จะขึ้นในหน้า **การสมัครสมาชิก** ว่า
"ยังไม่ได้ติดตั้งบนเซิร์ฟเวอร์นี้" ซึ่งเป็นสถานะปกติของบิลด์โอเพนซอร์ส
