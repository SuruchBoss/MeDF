# สถาปัตยกรรมของ MeDF

เอกสารนี้อธิบายการตัดสินใจเชิงออกแบบที่สำคัญ และจุดที่ต้องระวังเมื่อแก้ไขโค้ด

## ภาพรวม

```
เบราว์เซอร์ (หรือหน้าต่าง Electron)
        │
        │  ① แสดงผล: pdf.js เรนเดอร์หน้า PDF ลงแคนวาส
        │  ② แก้ไข: overlay elements วางทับด้วย DOM (ไม่แตะเนื้อหาต้นฉบับ)
        │  ③ บันทึกอัตโนมัติ: PATCH /api/documents/[id]
        ▼
Next.js server (route handlers)
        │
        │  ④ export: pdf-lib คัดลอกหน้าต้นฉบับ แล้ววาด overlay ทับ
        ▼
โฟลเดอร์ข้อมูล  MEDF_DATA_DIR
        ├── db.json                  สมาชิก · เมทาดาทาเอกสาร · ใบเสร็จ · การใช้งาน
        └── storage/
            ├── pdf/<id>.pdf         ไฟล์ต้นฉบับที่อัปโหลด (ไม่ถูกแก้ไข)
            ├── assets/<id>.png      รูปภาพที่วางในเอกสาร
            └── overlays/<id>.json   องค์ประกอบและสถานะหน้าของเอกสารนั้น
```

## หลักการหลัก: overlay ไม่ทำลายต้นฉบับ

MeDF ไม่แก้ไขเนื้อหาเดิมของ PDF และไม่แปลงหน้าเป็นรูปภาพ

- ไฟล์ที่อัปโหลดถูกเก็บไว้เหมือนเดิมตลอดอายุของเอกสาร
- การแก้ไขทั้งหมดถูกเก็บเป็น JSON แยก (`storage/overlays/<id>.json`)
- ตอน export หน้าต้นฉบับถูก **คัดลอก** ด้วย `copyPages` แล้ววาด overlay ทับ
  ข้อความและเวกเตอร์เดิมจึงยังคมชัด คัดลอกได้ และค้นหาได้

ผลที่ตามมา: การ "ลบ" ข้อความเดิมทำโดยวางกล่องทับ ซึ่งเป็นพฤติกรรมที่ตั้งใจ
และปลอดภัยกว่าการเขียนทับ content stream ของเอกสารสำคัญ

## ระบบพิกัด 3 ชั้น (ส่วนที่ต้องระวังที่สุด)

ตำแหน่งขององค์ประกอบทุกชิ้นถูกเก็บเป็น **จุด (point) ของ PDF** โดยมีจุดกำเนิดที่
**มุมซ้ายบน** และแกน y ชี้ลง — ซึ่งก็คือสิ่งที่ผู้ใช้เห็นบนหน้าจอ ไม่ใช่ระบบพิกัดของ PDF

| ชั้น | นิยาม | ที่มา |
| --- | --- | --- |
| **base display space** | สิ่งที่ผู้ใช้เห็นก่อนการหมุนหน้าที่ผู้ใช้สั่งเอง · origin ซ้ายบน · y ชี้ลง · ขนาด = `page.width × page.height` | เก็บพิกัดขององค์ประกอบทุกชิ้นในระบบนี้ |
| **page space** | ระบบพิกัดของหน้า PDF จริง (ยังไม่หมุน) · origin ซ้ายล่าง · y ชี้ขึ้น | `pageMatrix()` ใน `lib/pdf/matrix.ts` |
| **element space** | origin ที่มุมซ้ายล่างขององค์ประกอบ · y ชี้ขึ้น · หมุนรอบจุดกลางขององค์ประกอบ | `elementMatrix()` |

การวาดหนึ่งองค์ประกอบจึงใช้เมทริกซ์ `pageMatrix × elementMatrix` แล้วส่งเข้า
ตัวดำเนินการ `cm` ของ PDF ก่อนเรียกคำสั่งวาดของ pdf-lib

**เหตุผลที่แยก base display space ออกจากการหมุนของผู้ใช้:** เมื่อผู้ใช้สั่งหมุนหน้า
เนื้อหาต้นฉบับและองค์ประกอบที่วางไว้ต้องหมุนไปพร้อมกัน วิธีที่ทำให้ถูกต้องโดยไม่ต้อง
แปลงพิกัดขององค์ประกอบเลย คือ

- ฝั่งหน้าจอ: หมุน container ทั้งก้อนด้วย CSS `rotate()`
- ฝั่ง export: ตั้ง `/Rotate` ของหน้าปลายทางเป็น `การหมุนเดิมของไฟล์ + การหมุนที่ผู้ใช้สั่ง`
  โดย `pageMatrix()` คิดเฉพาะ **การหมุนเดิมของไฟล์** เท่านั้น

ส่วนการแปลงพิกัดของเมาส์ (และของ delta ระหว่างลาก) จาก "พื้นที่ที่หมุนแล้ว" กลับมาเป็น
base display space อยู่ใน `toBaseSpace()` / `deltaToBaseSpace()` ใน `components/editor/store.ts`

เทสต์ `npm run test:api` ตรวจเรื่องนี้ด้วยวิธีที่ไม่พึ่งโค้ดของเราเอง: มันวางข้อความที่พิกัดที่รู้ค่า
แล้วอ่านไฟล์ที่ export กลับมาด้วย pdf.js และใช้ `viewport.convertToViewportPoint()` ของ pdf.js
แปลงกลับเป็นพิกัดบนจอ แล้วเทียบกับค่าที่วางไว้ — ทั้งในหน้าปกติและหน้าที่หมุน 90°

## zoom กับความคมชัด

ในหน้าแก้ไข หนึ่งหน่วยของ base display space = 1 CSS pixel ที่ zoom 100%
การซูมทำด้วย `transform: scale(zoom)` บน container เดียว ดังนั้น

- ขนาดฟอนต์ ความหนาเส้น และระยะขอบ เขียนเป็นหน่วย pt ตรง ๆ ไม่ต้องคูณ zoom
- การตัดบรรทัดของข้อความไม่เปลี่ยนตาม zoom (เพราะสเกลทั้งก้อน) จึงตรงกับไฟล์ที่ export
- ส่วนควบคุมที่ต้องมีขนาดคงที่ (จุดจับ เส้นไกด์ กรอบเลือก) ถูกวาดไว้ **นอก** container ที่สเกล
  แล้วคูณพิกัดด้วย zoom เอง

ความละเอียดของ bitmap แยกจาก zoom: `renderScale` ขยับเป็นขั้น ๆ เพื่อไม่ให้ rasterise ใหม่ทุกครั้งที่ซูมเล็กน้อย
และหน้าที่อยู่ห่างจาก viewport จะไม่ถูกเรนเดอร์เลย (`useInView`) เพื่อให้เอกสารหลายร้อยหน้ายังเปิดได้

## ฟอนต์ไทย

pdf-lib ใช้ฟอนต์มาตรฐาน 14 ตัวของ PDF ซึ่งเข้ารหัสได้เฉพาะ WinAnsi — ภาษาไทยจึงกลายเป็นกล่องเปล่า
MeDF แก้ด้วยการฝังฟอนต์ **Sarabun** (แบบ subset ผ่าน fontkit) และ

- ถ้าข้อความมีอักขระที่ฟอนต์มาตรฐานเข้ารหัสไม่ได้ ระบบจะสลับไปใช้ Sarabun ให้อัตโนมัติ
  (`FontBook.resolve()` ใน `lib/pdf/fonts.ts`)
- ไฟล์ `.ttf` ชุดเดียวกันถูกเสิร์ฟให้เบราว์เซอร์เป็น `@font-face` ด้วย
  ทำให้เมทริกซ์ฟอนต์บนจอกับในไฟล์เป็นตัวเดียวกัน การตัดบรรทัดจึงตรงกัน
- การตัดบรรทัดตอน export (`wrapText()`) ตัดที่ช่องว่างก่อน แล้วถ้ายังยาวเกินจึงตัดทีละอักขระ
  ซึ่งเป็นพฤติกรรมเดียวกับ `overflow-wrap: break-word` ที่ใช้บนหน้าจอ (สำคัญกับภาษาไทยที่ไม่มีช่องว่าง)

### ข้อจำกัดที่ทราบ: สระอำ กับการคัดลอกข้อความ

fontkit จัดรูป (shape) สระอำ (ำ, U+0E33) เป็นสองกลิฟ ผลคือ

- **การแสดงผลถูกต้อง** ทั้งบนหน้าจอและในไฟล์ที่ export
- แต่ข้อความที่ **คัดลอกออกมาจากไฟล์** จะได้ `U+0E33 U+0E32` (ำ + า) แทน `U+0E33` ตัวเดียว
  จึงค้นหาคำที่มีสระอำ ในไฟล์ไม่เจอ

มีผลเฉพาะข้อความที่ **MeDF วาดเอง** (กล่องข้อความและเอกสารตัวอย่าง)
ข้อความเดิมของไฟล์ที่อัปโหลดถูกคัดลอกมาทั้งก้อนจึงไม่กระทบ
เทสต์ `npm run test:demo` ตรวจข้อนี้ไว้โดยเทียบแบบ normalise เพื่อให้พฤติกรรมนี้ถูกบันทึกไว้ในโค้ด

## เว็บเดโมแบบสถิต (GitHub Pages)

`apps/demo` คือ Next.js ที่ `output: 'export'` ซึ่ง **import คอมโพเนนต์ชุดเดียวกับ `apps/web`**
ผ่าน alias `@/*` จึงไม่มีการคัดลอกโค้ดหน้าเว็บไปไว้สองที่ และหน้าเดโมจะไม่เพี้ยนจากตัวจริง

สิ่งที่ทำให้หน้าแก้ไขทำงานได้โดยไม่มีเซิร์ฟเวอร์เลยคือ **ตัวเชื่อม (backend adapter)**
ใน `components/editor/backend.ts`

| | `createServerBackend` (ตัวจริง) | `DemoBackend` (เดโม) |
| --- | --- | --- |
| ไฟล์ต้นฉบับ | `GET /api/documents/:id/file` | `URL.createObjectURL` จากไฟล์ที่ผู้ใช้เลือก |
| บันทึก | `PATCH /api/documents/:id` | อยู่ใน state ของหน้าเท่านั้น |
| รูปภาพ | อัปโหลดเข้า `storage/assets` | blob ในหน้าเว็บ |
| Export | เรนเดอร์ที่เซิร์ฟเวอร์ | เรนเดอร์ในเบราว์เซอร์ด้วย **โค้ดเดียวกัน** |

`lib/pdf/render.ts` และ `lib/pdf/fonts.ts` จึงถูกทำให้เป็น isomorphic โดยรับ `FontLoader` เข้ามา
(`fonts-node.ts` อ่านจากดิสก์ · `fonts-browser.ts` ใช้ `fetch`) — ผลลัพธ์ที่ได้จากเดโมกับตัวจริงจึงเหมือนกัน

เทสต์ `npm run test:demo` ยืนยันเพิ่มว่า **ไม่มีการเรียก `/api/*` เลย** ระหว่างใช้งานหน้าเดโม
ซึ่งเป็นเงื่อนไขที่ทำให้มันเสิร์ฟเป็นไฟล์สถิตได้ ส่วน `npm run test:static` วางไฟล์ที่ export
ไว้ใต้ `/<repo>/` แล้วขับผ่านเบราว์เซอร์เหมือนที่ Pages จะเสิร์ฟจริง

## ชั้นข้อมูล

`src/lib/db.ts` เป็น persistence layer ขนาดเล็กที่ไม่พึ่งไลบรารีภายนอก

- ข้อมูลที่ต้องค้นหา (สมาชิก เมทาดาทาเอกสาร ใบเสร็จ การใช้งาน) อยู่ใน `db.json` ไฟล์เดียว
  เขียนแบบ atomic (เขียนไฟล์ temp แล้ว rename) และมี mutex ในโปรเซสกันการ read-modify-write ชนกัน
- ข้อมูลที่ใหญ่หรือถูกเขียนบ่อย (ไฟล์ PDF, รูปภาพ, overlay ของแต่ละเอกสาร) ถูกแยกเป็นไฟล์ต่างหาก
  การบันทึกอัตโนมัติจึงไม่ต้องเขียน index ทั้งก้อนใหม่
- ถ้า `db.json` เสียหาย ระบบจะ **ไม่** ลบทิ้ง แต่สำรองไว้เป็น `db.json.corrupt-<time>` และหยุดทำงาน

เหตุผลที่ไม่ใช้ฐานข้อมูลจริงตั้งแต่ต้น: ต้องแพ็กเป็นแอป Windows ที่ติดตั้งแล้วใช้ได้เลย
native module (เช่น better-sqlite3) หรือ query engine ของ Prisma ทำให้การแพ็กเปราะขึ้นมาก
ทุกการเข้าถึงข้อมูลอยู่หลัง `readDb()` / `mutate()` จึงเปลี่ยนไปใช้ Postgres ได้โดยไม่ต้องแก้ call site

## ความปลอดภัยและโควตา

- รหัสผ่านเข้ารหัสด้วย bcrypt (11 rounds) และการเทียบรหัสผ่านทำเสมอ แม้ไม่พบบัญชี เพื่อไม่ให้เวลาตอบสนองบอกใบ้
- เซสชันเป็น JWT (HS256) ใน cookie `httpOnly` + `sameSite=lax` และมี `sessionVersion`
  ที่ถูกเพิ่มค่าเมื่อเปลี่ยนรหัสผ่าน เพื่อยกเลิกเซสชันทุกอุปกรณ์
- การเข้าถึงเอกสารและรูปภาพตรวจความเป็นเจ้าของทุกครั้ง (404 ถ้าไม่มี, 403 ถ้าไม่ใช่ของตัวเอง)
- ชื่อไฟล์ใน storage ถูกสร้างโดยระบบและตรวจด้วย regex ทุกครั้งที่อ่าน จึงไม่มีทาง traverse ออกนอกโฟลเดอร์
- **โควตาและลายน้ำถูกบังคับตอน export ที่ฝั่งเซิร์ฟเวอร์** ไม่ใช่ที่ client
  การแก้ JavaScript ในเบราว์เซอร์จึงไม่ช่วยให้ข้ามข้อจำกัดของแพ็กเกจได้

## การบันทึกและ revision

การบันทึกอัตโนมัติจะหยุดรอ 1.2 วินาทีหลังการแก้ไขครั้งล่าสุด แล้วส่ง overlay ทั้งก้อน
พร้อม `baseRevision` ถ้าเลข revision บนเซิร์ฟเวอร์ไม่ตรง (เช่นเปิดเอกสารเดียวกันสองหน้าต่าง)
เซิร์ฟเวอร์จะตอบ `409` และหน้าจอจะบอกให้รีเฟรช แทนที่จะเขียนทับงานที่ใหม่กว่าเงียบ ๆ

ประวัติ undo/redo เก็บเป็น snapshot ของ overlay ทั้งก้อน โดยหนึ่งท่าลาก = หนึ่งขั้น undo
(กด pointer หนึ่งครั้ง = dispatch `checkpoint` หนึ่งครั้ง จากนั้น update ระหว่างลากไม่บันทึกประวัติ)

## แอป Windows

`desktop/` คือเชลล์ Electron บาง ๆ ที่

1. spawn เซิร์ฟเวอร์ Next.js แบบ standalone เป็น child process โดยใช้ไบนารีของ Electron เองในโหมด
   `ELECTRON_RUN_AS_NODE=1` (จึงไม่ต้องติดตั้ง Node.js บนเครื่องผู้ใช้)
2. ผูกเซิร์ฟเวอร์กับ `127.0.0.1` บนพอร์ตว่างที่หาได้ตอนเปิดโปรแกรม
3. ตั้ง `MEDF_DATA_DIR` ไปที่โฟลเดอร์ข้อมูลผู้ใช้ และสร้างกุญแจเซ็นเซสชันเก็บไว้ครั้งแรกที่รัน
4. รอให้พอร์ตตอบสนอง แล้วเปิด `BrowserWindow` ชี้ไปที่เซิร์ฟเวอร์นั้น

บันเดิลของเซิร์ฟเวอร์ถูกแพ็กเป็น `extraResources` (ไม่ใส่ใน `app.asar`)
เพราะ child process อ่านไฟล์จากใน archive ไม่ได้
