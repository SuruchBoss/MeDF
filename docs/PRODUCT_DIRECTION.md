# ทิศทางสินค้าและแผนระยะยาว

เอกสารนี้คือข้อตกลงว่า MeDF กำลังจะเป็นอะไร ทำไม และจะไปถึงตามลำดับไหน
เขียนขึ้นหลังทบทวนทิศทางเมื่อ 19 กันยายน 2026 — ตอนนั้น repo อายุ 1 วัน
มีโค้ด ~20,000 บรรทัด และมีผู้ใช้ 0 คน

> สถาปัตยกรรมปัจจุบันอยู่ที่ [ARCHITECTURE.md](ARCHITECTURE.md) — เอกสารนั้นอธิบาย
> ระบบที่มีอยู่ ส่วนเอกสารนี้อธิบายระบบที่กำลังจะกลายเป็น ที่ใดขัดกัน
> ให้ถือว่าเอกสารนี้คือปลายทาง และ ARCHITECTURE.md คือจุดตั้งต้น

## 1. สิ่งที่เปลี่ยน และเหตุผล

MeDF เริ่มต้นจากการเป็น **เว็บแอปแก้ PDF แบบวางทับ พร้อมระบบสมาชิกและแพ็กเกจรายเดือน**
การทบทวนพบว่าโครงสร้างนั้นไม่ตรงกับปัญหาที่ตั้งใจจะแก้ สามเรื่อง

**หนึ่ง — ปัญหาจริงคือ "ไม่มีไฟล์ต้นฉบับ" ไม่ใช่ "อยากวางของทับ PDF"**

ผู้ใช้เป้าหมายมี PDF อยู่ในมือ ไม่มีไฟล์ Word/InDesign ต้นทาง และต้องการแก้ข้อมูล
หรือจัดตำแหน่งใหม่ การไปขอไฟล์ต้นฉบับย้อนหลังมีต้นทุน (คนทำลาออกไปแล้ว
เอเจนซี่คิดเงิน ผ่านไปสองปีไม่มีใครหาไฟล์เจอ) เขาจึงมาหาเครื่องมือ

MeDF วันนี้ตอบปัญหานี้ไม่ได้ เพราะ `pdf.js` ถูกใช้เรนเดอร์ลงแคนวาสอย่างเดียว
ไม่เคยเรียก `getTextContent()` เลย และ `pdf-lib` ใช้ `copyPages()` คัดหน้าเดิมมาทั้งแผ่น
แล้ววาดทับ — **ในสายตาของโค้ดปัจจุบัน PDF ต้นฉบับคือรูปภาพ** วิธีเดียวที่ทำได้คือ
เอากล่องขาวทับข้อความเดิมแล้วพิมพ์ใหม่ ซึ่งผู้ใช้จับได้ทันทีว่าไม่ใช่ของจริง

**สอง — มูลค่าที่เก็บเงินได้อยู่ฝั่งเบราว์เซอร์ทั้งหมด**

การสกัดข้อความ จับคู่ฟอนต์ และตัดคำไทย ล้วนรันในเบราว์เซอร์ โมเดล open core
ที่มี guard สามชั้นคอยกันโค้ดฝั่งเซิร์ฟเวอร์ไม่หลุด จึงปกป้องสิ่งที่ไม่ได้อยู่ตรงนั้น

**สาม — ระบบสมาชิกสร้างภาระที่ไม่ได้แลกกับอะไร**

ถ้าไฟล์ไม่เคยถูกอัปโหลด เซิร์ฟเวอร์ไม่ได้ทำอะไรนอกจากเก็บรหัสผ่านที่ผู้ใช้จะลืม
และเก็บเอกสารที่สร้างภาระ PDPA ทั้งที่ระบบยังไม่มีแม้แต่ฟังก์ชันส่งอีเมลรีเซ็ตรหัสผ่าน
ลูกค้าที่จ่ายเงินแล้วลืมรหัสผ่านวันนี้จะเสียเอกสารถาวร

## 2. นิยามสินค้า

> **MeDF คือเครื่องมือแก้เอกสาร PDF ภาษาไทย สำหรับคนที่ไม่มีไฟล์ต้นฉบับแล้ว
> ทำงานในเบราว์เซอร์ ไฟล์ไม่เคยออกจากเครื่อง**

| แกน | จุดยืน |
| --- | --- |
| ปัญหา | แก้ PDF โดยไม่ต้องตามหาไฟล์ต้นฉบับ |
| จุดขายหัวหอก | **ภาษาไทยไม่พัง** — สระ วรรณยุกต์ และการตัดคำถูกต้อง ในจุดที่ Acrobat เพี้ยน |
| จุดขายที่ทำให้จ่ายเงิน | องค์กรที่ใช้ซอฟต์แวร์เถื่อนไม่ได้ และอัปโหลดเอกสารขึ้นคลาวด์ไม่ได้ |
| ตลาด | ไทย 100% — ธุรการ บัญชี HR ในองค์กรที่มีนโยบายลิขสิทธิ์ |
| ไม่ใช่ | ไม่ใช่เครื่องมือเซ็นเอกสาร · ไม่ใช่ merge/split/compress · ไม่ใช่ตลาดสากล |

### คู่แข่งที่ต้องเอาชนะ

คู่แข่งอันดับหนึ่งในไทยคือ **Acrobat / Foxit เถื่อน ราคา 0 บาท** แผนที่ไม่มีคำตอบให้ข้อนี้
คือแผนที่ใช้ไม่ได้ คำตอบของ MeDF มีสองชั้น

1. **ของเถื่อนก็แก้ภาษาไทยพังเหมือนกัน** — Acrobat วางสระและวรรณยุกต์ผิดตำแหน่ง
   และเปลี่ยนฟอนต์เองเวลาแก้ข้อความไทย เป็นข้อบกพร่องที่เงิน 0 บาทซื้อทางแก้ไม่ได้
   และพิสูจน์ได้ด้วยภาพเปรียบเทียบภาพเดียว
2. **บางองค์กรใช้ของเถื่อนไม่ได้** — มีนโยบาย IT โดนตรวจลิขสิทธิ์ หรือมีบริษัทแม่
   ต่างชาติ กลุ่มนี้คือคนที่กดจ่ายจริง เพราะ "ฟรี" ไม่เคยเป็นตัวเลือกของเขาตั้งแต่แรก

การที่ core เป็นโอเพนซอร์สตรวจสอบได้ คือส่วนหนึ่งของคำตอบข้อ 2 ไม่ใช่แค่อุดมการณ์

## 3. ความจริงทางเทคนิค: ไม่ใช่ทุกไฟล์ที่แก้ได้

นี่คือข้อจำกัดที่ต้องบอกผู้ใช้ตั้งแต่วินาทีที่เขาลากไฟล์เข้ามา ไม่ใช่ให้เขาค้นพบเอง
ตอนแก้ไปครึ่งทาง

| ชั้น | ที่มาของไฟล์ | สถานะ | MeDF ทำอะไรได้ |
| --- | --- | --- | --- |
| **A** | Word · Excel · Google Docs | สกัดข้อความได้ครบ มี ToUnicode | **แก้ข้อความเดิมได้จริง** |
| **B** | InDesign · Illustrator · Canva | สกัดได้ แต่ฟอนต์เป็น subset | แก้ได้ แต่เตือนว่าฟอนต์จะเปลี่ยน |
| **C** | สแกนกระดาษ | เป็นรูปล้วน ไม่มีชั้นข้อความ | วางทับอย่างเดียว (OCR = ปีที่ 2+) |
| **D** | encoding เสีย | สกัดออกมาเป็นอักขระขยะ | วางทับอย่างเดียว |

**เป้าหมายปีแรกคือชั้น A เท่านั้น** ชั้น B ทำได้เท่าที่ได้ ชั้น C และ D ถอยไปใช้
โหมดวางทับแบบที่ MeDF ทำได้อยู่แล้ววันนี้ ซึ่งยังมีประโยชน์และไม่ได้ถูกทิ้ง

### กับดักเฉพาะภาษาไทย

สามข้อนี้คือเหตุผลที่เครื่องมือต่างชาติทำภาษาไทยได้ไม่ดี และเป็นช่องของ MeDF

1. **หนึ่งบรรทัดคือ run ย่อยหลายสิบชิ้น** — PDF ภาษาไทยมักวางทีละ glyph พร้อมพิกัด
   ของตัวเอง ต้องจับกลับมารวมเป็นบรรทัดเดียวก่อนถึงจะแก้ได้
2. **สระบน-ล่างและวรรณยุกต์ถูกวางด้วย offset มือ** ไม่ได้พึ่ง shaping ของฟอนต์
   การ round-trip ให้ถูกคือจุดที่ Acrobat แพ้ และคือจุดที่ต้องทำให้ถูกที่สุด
3. **ไทยไม่มีช่องว่างระหว่างคำ** — แก้ข้อความแล้วต้องตัดบรรทัดใหม่ ใช้
   `Intl.Segmenter('th', { granularity: 'word' })` ของเบราว์เซอร์ ไม่ต้องเขียนเอง

## 4. สถาปัตยกรรมปลายทาง

```
เบราว์เซอร์ (ติดตั้งเป็น PWA ได้ ใช้ออฟไลน์ได้)
        │
        │  ① pdf.js เรนเดอร์ลงแคนวาส + getTextContent() สกัดข้อความเดิม
        │  ② จำแนกชั้นไฟล์ แล้วบอกผู้ใช้ตรง ๆ ว่าไฟล์นี้แก้ได้แค่ไหน
        │  ③ แก้ข้อความเดิมในที่ (ชั้น A) หรือวางทับ (ชั้น B/C/D)
        │  ④ บันทึกลง IndexedDB — ไม่มีการอัปโหลด
        │  ⑤ pdf-lib ลบ text operator เดิมออกจาก content stream แล้ววาดใหม่
        ▼
ไฟล์ .medf บนเครื่องผู้ใช้  ·  ไฟล์ PDF ที่ export ออกมา

เซิร์ฟเวอร์: ไม่มี
การปลดล็อก: license key เซ็นด้วย ed25519 ตรวจในเบราว์เซอร์ด้วย WebCrypto
```

### หลักการที่ห้ามละเมิด

- **ไฟล์ของผู้ใช้ไม่ออกจากเครื่อง** — ไม่มี endpoint ไหนรับไฟล์ PDF ไม่มี telemetry
  ที่ส่งเนื้อหาเอกสาร สถิติที่เก็บได้มีแค่ตัวเลขรวม (ชั้นของไฟล์ จำนวนหน้า) และ
  ต้องขออนุญาตก่อน
- **บอกความจริงก่อนผู้ใช้เสียเวลา** — ถ้าไฟล์แก้ข้อความไม่ได้ ต้องรู้ภายในไม่กี่วินาที
  แรก พร้อมเหตุผลที่อ่านรู้เรื่อง
- **การตรวจ license ทำงานออฟไลน์ได้** — คนที่ซื้อไปแล้วต้องใช้ได้ตลอดไปแม้เว็บนี้จะหายไป

### การเก็บงานของผู้ใช้

| ที่เก็บ | ใช้ทำอะไร |
| --- | --- |
| IndexedDB | งานที่กำลังทำ บันทึกอัตโนมัติ เปิดต่อได้เมื่อกลับมา |
| ไฟล์ `.medf` บนเครื่อง | zip ของ PDF ต้นฉบับ + overlay JSON — ผู้ใช้กดบันทึกเอง ย้ายเครื่องได้ |
| PDF ที่ export | ผลลัพธ์สุดท้าย |

ต้องมีคำเตือนชัดเจนว่าการล้างข้อมูลเบราว์เซอร์จะลบงานใน IndexedDB
และต้องชวนให้บันทึกเป็นไฟล์ `.medf`

## 5. โมเดลธุรกิจ

> **ข้อสมมติที่ยังไม่ยืนยัน** — ตัวเลขราคาด้านล่างมาจากข้อเสนอแนะ ยังไม่ผ่าน
> การตัดสินใจขั้นสุดท้าย แก้ได้โดยไม่กระทบแผนงานก่อนสัปดาห์ที่ 13

**ซื้อขาด 1,490 บาท + ต่ออายุอัปเดตปีละ 690 บาท (ไม่บังคับ)**

เวอร์ชันที่ซื้อไปใช้ได้ตลอดชีพไม่ว่าจะต่ออายุหรือไม่ การต่ออายุซื้อเฉพาะสิทธิ์รับ
เวอร์ชันใหม่ เหตุผลที่เลือกแบบนี้แทนรายเดือนหรือรายปีบังคับ

- ไม่ต้องมีระบบอีเมลทวงต่ออายุ เพราะพลาดต่ออายุแล้วไม่เกิดอะไรเลย
- key ฝังวันที่ "อัปเดตถึง" แล้วตรวจในเบราว์เซอร์ **ไม่ต้องมีเซิร์ฟเวอร์เลย**
- ไม่มีดราม่า "จ่ายเงินแล้วแต่เข้าไม่ได้" ซึ่งเป็นสาเหตุรีวิวแย่อันดับต้นของเครื่องมือแบบนี้

### เส้นแบ่งฟรีกับจ่ายเงิน

| | ฟรี | จ่ายแล้ว |
| --- | --- | --- |
| วางทับ องค์ประกอบ 8 ชนิด export | ครบ | ครบ |
| ตรวจและบอกชั้นของไฟล์ | ได้ | ได้ |
| **แก้ข้อความเดิมในไฟล์** | ดูตัวอย่างได้ แก้ได้จำกัด | ไม่จำกัด |
| ลายน้ำตอน export | มี | ไม่มี |

เส้นแบ่งย้ายมาอยู่ที่ **"แก้ข้อความเดิม"** ไม่ใช่ที่จำนวนเอกสารหรือจำนวน export
เพราะนั่นคือสิ่งเดียวที่คู่แข่งฟรีทำไม่ได้ และเป็นสิ่งเดียวที่มีต้นทุนการสร้างจริง

### การส่งมอบ key

**30 ลูกค้าแรกออก key ด้วยมือ** — Stripe Payment Link (ไม่ต้องเขียนโค้ด) รับเงิน
แล้วรันสคริปต์ออก key ส่งอีเมลเอง ที่ 30 คนคือ 30 ครั้งใน 6 เดือน ไม่คุ้มกับการเขียน
ระบบอัตโนมัติ และการได้คุยกับลูกค้าทุกคนในช่วงนี้มีค่ามากกว่าเวลาที่ประหยัดได้

## 6. สิ่งที่ต้องพัก รื้อ และเขียนใหม่

โค้ดที่ "พัก" ให้ย้ายไป branch เก็บไว้ ไม่ลบทิ้ง เผื่อกลับมาใช้

| สถานะ | รายการ | ปลายทาง |
| --- | --- | --- |
| **พัก** | `desktop/` ทั้งโฟลเดอร์ (Electron + installer) | branch `archive/desktop` |
| **พัก** | `api/auth/*` `api/documents/*` `api/assets/*` `api/billing/*` | branch `archive/server` |
| **พัก** | `lib/db.ts` `lib/storage.ts` โควตา หน้า admin | branch `archive/server` |
| **รื้อทิ้ง** | `scripts/guard-private.mjs` `install-hooks.mjs` `scaffold-pro.mjs` `lib/pro.ts` | ลบ |
| **เขียนใหม่** | `docs/OPEN_CORE.md` → เหลือหน้าเดียวอธิบายว่าทำไมบางโค้ดไม่อยู่ที่นี่ | แทนที่ |
| **ยุบรวม** | `apps/demo` + `apps/web` → เหลือแอปสถิตตัวเดียว | ยุบ |
| **ลดรูป** | `lib/plans.ts` 3 แพ็กเกจ → เหลือ ฟรี / จ่ายแล้ว | แก้ |
| **เก็บไว้ทั้งหมด** | เอนจิน overlay · การฝัง Sarabun · snap/undo · ท่อ export · i18n · unit tests | ไม่แตะ |

ผลข้างเคียงสำคัญ: **เมื่อไม่มีเซิร์ฟเวอร์ ทั้งแอปกลายเป็นเว็บสถิต** `apps/demo` ที่สร้าง
ขึ้นมาเพื่อ GitHub Pages จึงไม่มีเหตุผลให้มีอยู่ต่อ การยุบสอง workspace เหลือหนึ่ง
ตัดทั้ง build pipeline typecheck และ `static-test.mjs` ออกไปชุดหนึ่ง

### ขอบเขตโอเพนซอร์ส

> **ข้อสมมติที่ยังไม่ยืนยัน**

core ยังเป็น **MIT** ทั้งหมดตามเดิม — เอนจิน overlay การจำแนกชั้นไฟล์ export PWA
ส่วน **โมดูลแก้ข้อความเดิม** อยู่ repo ส่วนตัว ไม่ใช่ MIT ต่อเข้ามาเป็น dependency ธรรมดา
ไม่มี guard ไม่มี scaffold ไม่มีพิธีกรรม — แค่แพ็กเกจที่ไม่ได้เผยแพร่

## 9. ปีที่ 1 และปีที่ 2

**ปีที่ 1 (ถึงราวไตรมาส 3 ปี 2027)** — ทำชั้น A ให้ดีจนไม่มีใครเถียง ขยายจาก 10 คนแรก
ไปหากลุ่ม Facebook และการบอกต่อ เก็บสถิติว่าไฟล์ที่แก้ไม่ได้เป็นเพราะอะไร
เพื่อตัดสินใจว่าปีที่ 2 ควรไปทางไหน ไม่เพิ่มฟีเจอร์ใหม่ที่ไม่เกี่ยวกับการแก้ข้อความ

**ต้นปีที่ 2 — PDF → DOCX** คือการคืนไฟล์ต้นฉบับให้ผู้ใช้ไปแก้ใน Word ต่อ ซึ่งตอบ
ปัญหา "ไม่มีไฟล์ต้นฉบับ" ตรงกว่าการสร้าง reflow engine ใน MeDF เอง
ข้อนี้จะเริ่มก็ต่อเมื่อคุณภาพของชั้น A ดีพอแล้วเท่านั้น

**สิ่งที่ตัดสินใจแล้วว่าไม่ทำ** — reflow engine เต็มรูปแบบแบบ Word (Acrobat ที่มีทีม
เป็นร้อยคนยังทำได้ไม่ดี) · ตลาดต่างประเทศ · ระบบทีมและที่นั่ง · แอปมือถือ ·
OCR จนกว่าสถิติจะบอกว่าไฟล์ชั้น C เยอะจริง
